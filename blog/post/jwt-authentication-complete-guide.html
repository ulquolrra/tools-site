📚 第一部分：JWT基础概念

1.1 什么是JWT？

JWT（JSON Web Token）是一个开放标准（RFC 7519），它定义了一种紧凑且自包含的方式，用于在各方之间安全地传输信息，作为JSON对象。JWT可以被验证和信任，因为它是数字签名的。

JWT的特点
  • 紧凑性（Compact）：JWT可以通过URL、POST参数或者HTTP Header发送，因为它的大小非常小
  • 自包含（Self-contained）：payload中包含了用户所需的所有信息，避免了多次查询数据库
  • 可扩展性（Extensible）：JWT的头部和负载可以添加自定义字段，适应各种场景
  • 安全性（Secure）：JWT使用数字签名确保其完整性，防止被篡改

1.2 JWT vs Session：两种认证方式的对比

传统的Session认证和JWT认证各有优缺点，选择哪种方式取决于你的应用场景：

Session vs JWT 对比
特性SessionJWT
存储位置 服务器端（通常在内存或数据库中） 客户端（浏览器localStorage或cookie中）
扩展性 差（需要Session同步或共享存储） 好（无状态，易于水平扩展）
性能 中等（每次请求需要查询服务器） 好（验证Token不需要查询服务器）
安全性 依赖服务器安全性 依赖Token签名算法和密钥安全性
过期处理 服务器端控制 客户端控制（需要刷新Token）
数据大小 小（通常只有Session ID） 中等（包含用户数据）
适用场景 传统Web应用，需要服务器端控制 API服务、SPA、移动应用
我们的建议：对于新项目，特别是API服务或SPA（单页应用），我们强烈推荐使用JWT认证。对于传统服务器端渲染的Web应用，Session认证可能更合适。也可以考虑混合使用：前端使用JWT，后端使用Session。

🔍 第二部分：JWT的结构

2.1 JWT的组成部分

JWT由三个部分组成，用点（.）分隔：

xxxxx.yyyyy.zzzzz
  • Header（头部）：包含Token的类型和使用的签名算法
  • Payload（负载）：包含声明（claims），即关于实体（通常是用户）和其他数据的陈述
  • Signature（签名）：用于验证Token的完整性，防止被篡改

2.2 Header（头部）

Header包含两个部分：

  • alg：签名算法（algorithm），常见的有HS256、RS256、ES256等
  • typ：Token类型（type），通常为"JWT"

示例：

{
  "alg": "HS256",
  "typ": "JWT"
}

这个JSON对象会被Base64URL编码（注意：不是标准的Base64编码，而是URL安全的Base64变体）形成JWT的第一部分。

Base64URL编码示例

标准的Base64编码会使用+、/和=字符，这些字符在URL中不安全。因此JWT使用Base64URL编码，将：

  • + 替换为 -
  • / 替换为 _
  • =（padding）被省略

你可以使用我们的Base64编解码工具来查看Base64和Base64URL的区别。

2.3 Payload（负载）

Payload包含声明（Claims）。声明是关于实体（通常是用户）和其他数据的陈述。声明有三种类型：

声明的三种类型
  • 注册声明（Registered claims）：预定义的声明，如iss（签发者）、exp（过期时间）、sub（主题）、aud（受众）等。这些声明不是强制的，但是推荐的。
  • 公共声明（Public claims）：可以由使用JWT的各方自定义的声明，但为了避免冲突，应该使用IANA JSON Web Token Registry中定义的名称，或者使用包含防冲突命名空间的URI。
  • 私有声明（Private claims）：自定义声明，用于在同意使用它们的各方之间共享信息。

常见的注册声明：

声明全称描述
issIssuer签发者，标识发出JWT的实体
subSubject主题，通常是用户ID
audAudience受众，标识JWT的接收方
expExpiration Time过期时间，标识JWT的过期时间（Unix时间戳）
nbfNot Before生效时间，标识JWT在什么时间之前不能被接受（Unix时间戳）
iatIssued At签发时间，标识JWT的签发时间（Unix时间戳）
jtiJWT IDJWT唯一标识符，用于防止重放攻击

Payload示例：

{
  "sub": "1234567890",
  "name": "John Doe",
  "admin": true,
  "iat": 1516239022,
  "exp": 1516242622
}

这个JSON对象也会被Base64URL编码，形成JWT的第二部分。

2.4 Signature（签名）

签名用于验证Token的完整性，确保Token在传输过程中没有被篡改。签名的生成方式取决于Header中指定的算法：

2.4.1 HMAC SHA-256（HS256）

使用HMAC SHA-256算法生成签名：

HMACSHA256(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  secret
)

特点：使用对称密钥（secret），即签名和验证都使用同一个密钥。适用于服务器既是JWT的签发者也是验证者的情况。

2.4.2 RSA SHA-256（RS256）

使用RSA SHA-256算法生成签名：

RSA(
  base64UrlEncode(header) + "." + base64UrlEncode(payload),
  privateKey
)

特点：使用非对称密钥对（私钥和公钥）。私钥用于签名，公钥用于验证。适用于JWT的签发者和验证者不同的情况。

2.4.3 ECDSA SHA-256（ES256）

使用ECDSA（椭圆曲线数字签名算法）SHA-256生成签名。与RS256类似，使用非对称密钥对，但使用椭圆曲线密码学，提供相同安全级别下更短的密钥长度。

算法选择建议：
  • HS256：适用于大多数应用场景，简单且性能良好
  • RS256/ES256：适用于需要更高安全级别的场景，或者JWT的签发者和验证者不同的情况
  • 避免使用：HS1（SHA-1）和RS1/ES1，因为SHA-1已被证明不安全

🔧 第三部分：JWT的工作流程

3.1 JWT认证流程

JWT认证的典型流程如下：

JWT认证流程图
  1. 用户登录：用户提供用户名和密码
  2. 服务器验证：服务器验证用户凭据，确认无误后生成JWT
  3. 返回Token：服务器将JWT返回给客户端（通常在HTTP响应头中）
  4. 客户端存储：客户端存储Token（通常在localStorage、sessionStorage或cookie中）
  5. 请求API：客户端在后续请求中附带Token（通常在Authorization头中）
  6. 服务器验证：服务器验证Token的签名和有效性，如果有效则处理请求
  7. 返回响应：服务器返回响应给客户端

💻 第四部分：JWT的代码实现

4.1 Node.js中使用JWT

Node.js中使用JWT需要安装jsonwebtoken包：

npm install jsonwebtoken

4.1.1 生成JWT

const jwt = require('jsonwebtoken');

// 定义secret密钥（应从环境变量中获取）
const secret = process.env.JWT_SECRET || 'your-256-bit-secret';

// 创建Payload
const payload = {
  sub: '1234567890',
  name: 'John Doe',
  admin: true,
  iat: Math.floor(Date.now() / 1000),
  exp: Math.floor(Date.now() / 1000) + (60 * 60) // 1小时后过期
};

// 生成JWT
const token = jwt.sign(payload, secret, { algorithm: 'HS256' });

console.log('Generated Token:', token);
// 输出：eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4gRG9lIiwiYWRtaW4iOnRydWUsImlhdCI6MTY5NTIyNjQ0MiwiZXhwIjoxNjk1MjI5NjQyfQ.abc123...

4.1.2 验证JWT

const jwt = require('jsonwebtoken');
const secret = process.env.JWT_SECRET || 'your-256-bit-secret';

// 验证Token
jwt.verify(token, secret, { algorithms: ['HS256'] }, (err, decoded) => {
  if (err) {
    // Token验证失败
    console.error('Token verification failed:', err.message);
    // err可能的值：
    // - JsonWebTokenError: invalid token
    // - TokenExpiredError: jwt expired
    // - NotBeforeError: jwt not active
    return;
  }
  
  // Token验证成功，decoded包含解码后的Payload
  console.log('Decoded payload:', decoded);
  // 输出：{ sub: '1234567890', name: 'John Doe', admin: true, iat: 1695226442, exp: 1695230042 }
});

4.1.3 完整的登录和验证示例

const express = require('express');
const jwt = require('jsonwebtoken');
const bcrypt = require('bcryptjs');

const app = express();
app.use(express.json());

const JWT_SECRET = process.env.JWT_SECRET || 'your-256-bit-secret';
const JWT_EXPIRES_IN = '1h';

// 模拟用户数据库
const users = [
  { id: 1, username: 'john', password: bcrypt.hashSync('password123', 8) },
  { id: 2, username: 'jane', password: bcrypt.hashSync('password456', 8) }
];

// 登录路由
app.post('/login', (req, res) => {
  const { username, password } = req.body;
  
  // 查找用户
  const user = users.find(u => u.username === username);
  if (!user) {
    return res.status(401).json({ message: '用户不存在' });
  }
  
  // 验证密码
  const isPasswordValid = bcrypt.compareSync(password, user.password);
  if (!isPasswordValid) {
    return res.status(401).json({ message: '密码错误' });
  }
  
  // 生成Token
  const token = jwt.sign(
    { sub: user.id, username: user.username },
    JWT_SECRET,
    { expiresIn: JWT_EXPIRES_IN }
  );
  
  res.json({ token });
});

// 受保护的路由
app.get('/protected', (req, res) => {
  const token = req.headers.authorization?.split(' ')[1];
  
  if (!token) {
    return res.status(401).json({ message: '未提供Token' });
  }
  
  jwt.verify(token, JWT_SECRET, (err, decoded) => {
    if (err) {
      return res.status(401).json({ message: '无效的Token', error: err.message });
    }
    
    // Token有效，可以访问受保护的资源
    res.json({ 
      message: '访问成功', 
      user: decoded 
    });
  });
});

// 刷新Token路由
app.post('/refresh', (req, res) => {
  const token = req.headers.authorization?.split(' ')[1];
  
  if (!token) {
    return res.status(401).json({ message: '未提供Token' });
  }
  
  jwt.verify(token, JWT_SECRET, { ignoreExpiration: true }, (err, decoded) => {
    if (err) {
      return res.status(401).json({ message: '无效的Token' });
    }
    
    // 生成新的Token
    const newToken = jwt.sign(
      { sub: decoded.sub, username: decoded.username },
      JWT_SECRET,
      { expiresIn: JWT_EXPIRES_IN }
    );
    
    res.json({ token: newToken });
  });
});

app.listen(3000, () => {
  console.log('服务器运行在 http://localhost:3000');
});

4.2.2 在前端应用中存储和使用JWT

// 登录后存储Token
function login(token) {
  // 通常存储在localStorage或sessionStorage中
  localStorage.setItem('token', token);
  
  // 或者存储在内存中（页面刷新后会丢失）
  sessionStorage.setItem('token', token);
  
  // 设置默认的Authorization头
  axios.defaults.headers.common['Authorization'] = `Bearer ${token}`;
}

// 登出时清除Token
function logout() {
  localStorage.removeItem('token');
  sessionStorage.removeItem('token');
  delete axios.defaults.headers.common['Authorization'];
}

// 检查是否已登录
function isAuthenticated() {
  const token = localStorage.getItem('token');
  if (!token) return false;
  
  try {
    const payload = KJUR.jws.JWS.parse(token);
    const now = Math.floor(Date.now() / 1000);
    
    // 检查Token是否过期
    if (payload.payloadObj.exp && payload.payloadObj.exp < now) {
      return false;
    }
    
    return true;
  } catch (e) {
    return false;
  }
}

// 在Axios请求中自动附带Token
axios.interceptors.request.use(config => {
  const token = localStorage.getItem('token');
  if (token) {
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
}, error => {
  return Promise.reject(error);
});

// 处理Token过期
axios.interceptors.response.use(response => response, error => {
  if (error.response && error.response.status === 401) {
    // Token过期，尝试刷新Token
    const originalRequest = error.config;
    
    if (!originalRequest._retry) {
      originalRequest._retry = true;
      
      return axios.post('/refresh')
        .then(response => {
          const newToken = response.data.token;
          localStorage.setItem('token', newToken);
          axios.defaults.headers.common['Authorization'] = `Bearer ${newToken}`;
          originalRequest.headers['Authorization'] = `Bearer ${newToken}`;
          return axios(originalRequest);
        });
    }
  }
  
  return Promise.reject(error);
});
浏览器安全注意事项：
  • 不要将敏感信息存储在JWT中：JWT可以被解码，任何人都可以看到其中的内容（虽然不能修改，除非知道密钥）
  • 使用HTTPS：JWT应该通过HTTPS传输，防止中间人攻击
  • 设置合理的过期时间：Token的过期时间应该尽可能短，减少风险
  • 避免XSS攻击：如果Token存储在localStorage中，要注意防止XSS攻击窃取Token

🔒 第五部分：JWT安全最佳实践

5.1 JWT使用的最佳实践

虽然JWT非常有用，但不当使用会带来安全风险。以下是我们总结的JWT使用最佳实践：

JWT安全清单
  1. 使用强算法：使用HS256、RS256或ES256，避免使用HS1、RS1、ES1等不安全的算法
  2. 密钥安全：密钥（secret或private key）应该足够长且随机，并安全存储。对于HS256，密钥至少256位（32字节）
  3. 设置过期时间：为Token设置合理的过期时间。对于访问Token（Access Token），建议15-60分钟；对于刷新Token（Refresh Token），建议7-30天
  4. 使用HTTPS：JWT必须通过HTTPS传输，防止中间人攻击
  5. 最小化Payload：在Payload中只包含必要的信息，避免存储敏感数据
  6. 验证所有声明：在验证Token时，要验证所有必须的声明，包括exp、nbf、aud等
  7. 使用jti防止重放：为每个Token分配唯一的jti（JWT ID），防止Token重放攻击
  8. 处理Token撤销：实现Token黑名单机制，允许在必要时撤销Token
  9. 限制Token使用：为每个Token指定具体的受众（aud），限制其使用范围
  10. 记录和监控：记录JWT的使用情况，监控异常行为

5.2 JWT常见安全漏洞

了解JWT的常见安全漏洞，可以帮助你避免这些问题：

5.2.1 算法混淆攻击（Algorithm Confusion Attack）

如果服务器接受多种算法（如HS256和RS256），并且没有正确验证算法，攻击者可能会使用公钥作为HS256的密钥进行签名，从而绕过验证。

防护措施：在验证Token时，必须明确指定允许的算法列表，不要使用jwt.verify(token, secret)，而要使用jwt.verify(token, secret, { algorithms: ['HS256'] })。

5.2.2 密钥泄露

如果密钥（secret或private key）被泄露，攻击者可以伪造任何Token。HS256算法特别容易受到这个攻击的影响，因为密钥通常在多个服务器之间共享。

防护措施：
  • 密钥应该足够长且随机（至少256位）
  • 密钥应该安全存储，不能硬编码在代码中
  • 使用环境变量或密钥管理服务存储密钥
  • 定期轮换密钥
  • 对于HS256，每个服务器可以使用不同的密钥
  • 对于RS256/ES256，私钥必须安全存储，公钥可以公开

5.2.3 Token过期时间过长

如果Token的过期时间设置得过长，一旦Token被泄露，攻击者可以长时间使用它。特别是对于Access Token，过期时间应该尽可能短。

防护措施：
  • Access Token的过期时间建议设置为15-60分钟
  • Refresh Token的过期时间可以更长（7-30天）
  • 实现Token自动刷新机制
  • 为用户提供显式的登出功能，撤销Token

5.2.4 不验证声明

如果服务器在验证Token时没有验证exp（过期时间）、nbf（生效时间）、aud（受众）等声明，可能会导致安全问题。

防护措施：在验证Token时，必须验证所有相关的声明，确保Token在有效期内，并且是针对当前服务的。

🚀 第六部分：JWT高级应用

6.1 刷新Token（Refresh Token）

为了平衡用户体验和安全性，通常会使用两个Token：

  • Access Token（访问Token）：用于访问受保护的API，过期时间短（15-60分钟）
  • Refresh Token（刷新Token）：用于获取新的Access Token，过期时间长（7-30天）

工作流程：

  1. 用户登录，服务器返回Access Token和Refresh Token
  2. 客户端使用Access Token访问API
  3. 当Access Token过期时，客户端使用Refresh Token获取新的Access Token
  4. 如果Refresh Token也过期了，用户需要重新登录

实现示例：

// 登录时返回两个Token
app.post('/login', (req, res) => {
  const { username, password } = req.body;
  
  // 验证用户凭据...
  
  // 生成Access Token（过期时间15分钟）
  const accessToken = jwt.sign(
    { sub: user.id, type: 'access' },
    JWT_ACCESS_SECRET,
    { expiresIn: '15m' }
  );
  
  // 生成Refresh Token（过期时间7天）
  const refreshToken = jwt.sign(
    { sub: user.id, type: 'refresh' },
    JWT_REFRESH_SECRET,
    { expiresIn: '7d' }
  );
  
  // 存储Refresh Token到数据库（用于撤销）
  await saveRefreshToken(user.id, refreshToken);
  
  res.json({ accessToken, refreshToken });
});

// 刷新Access Token
app.post('/refresh', (req, res) => {
  const { refreshToken } = req.body;
  
  // 验证Refresh Token
  jwt.verify(refreshToken, JWT_REFRESH_SECRET, async (err, decoded) => {
    if (err) {
      return res.status(401).json({ message: '无效的刷新Token' });
    }
    
    // 检查Refresh Token是否被撤销
    const isRevoked = await isRefreshTokenRevoked(refreshToken);
    if (isRevoked) {
      return res.status(401).json({ message: '刷新Token已被撤销' });
    }
    
    // 生成新的Access Token
    const newAccessToken = jwt.sign(
      { sub: decoded.sub, type: 'access' },
      JWT_ACCESS_SECRET,
      { expiresIn: '15m' }
    );
    
    // 可选：生成新的Refresh Token（旋转Token）
    const newRefreshToken = jwt.sign(
      { sub: decoded.sub, type: 'refresh' },
      JWT_REFRESH_SECRET,
      { expiresIn: '7d' }
    );
    
    // 撤销旧的Refresh Token
    await revokeRefreshToken(refreshToken);
    
    // 存储新的Refresh Token
    await saveRefreshToken(decoded.sub, newRefreshToken);
    
    res.json({ 
      accessToken: newAccessToken,
      refreshToken: newRefreshToken 
    });
  });
});

// 登出时撤销Refresh Token
app.post('/logout', (req, res) => {
  const { refreshToken } = req.body;
  
  await revokeRefreshToken(refreshToken);
  
  res.json({ message: '登出成功' });
});

6.2 JWT存储最佳实践

JWT可以存储在多个位置，每个位置都有其优缺点：

JWT存储选项对比
存储位置优点缺点推荐用途
localStorage 数据持久化，页面刷新后仍然存在 容易受到XSS攻击 需要防XSS的应用
sessionStorage 页面会话结束后自动清除 页面刷新后会丢失 需要会话级存储的应用
Cookie 自动附带到HTTP请求中，可以设置HttpOnly防XSS 容易受到CSRF攻击，需要CSRF保护 传统Web应用
内存（Memory） 完全避免XSS和CSRF攻击 页面刷新后会丢失 SPA应用

我们的建议：

  • 对于SPA应用：使用内存存储，配合HttpOnly Cookie存储刷新Token
  • 对于传统Web应用：使用HttpOnly Cookie存储，配合CSRF保护
  • 如果必须使用localStorage：确保有完善的XSS防护措施

📊 第七部分：JWT使用案例

7.1 案例一：电商平台的用户认证

背景：一个电商平台需要为用户提供登录功能，同时需要保护用户的订单信息和个人数据。

解决方案：

  • 用户登录：用户提供用户名和密码，服务器验证后返回JWT
  • Token结构：Payload包含用户ID、用户名、用户角色（普通用户/管理员）
  • Token有效期：Access Token 15分钟，Refresh Token 7天
  • API保护：所有需要认证的API都需要在Authorization头中提供有效的JWT
  • 权限控制：根据Token中的用户角色控制API访问权限

效果：用户体验良好，API响应速度快，系统扩展性好。

7.2 案例二：API网关的认证和授权

背景：一个微服务架构的应用，需要通过API网关统一处理认证和授权。

解决方案：

  • JWT签发：由认证服务签发JWT
  • JWT验证：由API网关统一验证JWT
  • 权限声明：JWT Payload中包含用户的权限信息
  • 服务间通信：各个微服务通过API网关相互通信，附带JWT
  • 缓存策略：API网关缓存JWT验证结果，提升性能

效果：统一的认证和授权，各个微服务无需处理认证逻辑，架构清晰。

7.3 案例三：第三方API的访问

背景：一个应用需要调用第三方API，第三方API使用JWT进行认证。

解决方案：

  • 客户端凭证：从第三方获取Client ID和Client Secret
  • 获取Token：使用Client ID和Client Secret获取JWT
  • API调用：在调用第三方API时附带JWT
  • Token管理：定期刷新Token，确保不会过期
  • 错误处理：处理Token过期、无效等情况

效果：成功集成第三方API，实现应用功能。

🎯 总结

JWT（JSON Web Token）是一种强大的认证和授权机制，特别适合用于现代Web应用和API服务。本文从JWT的基础概念出发，详细介绍了JWT的结构、工作流程、代码实现、安全最佳实践和高级应用，希望能帮助你全面理解和正确使用JWT。

关键要点：

  1. JWT = Header + Payload + Signature，三部分通过Base64URL编码并用点连接
  2. JWT的特点：紧凑、自包含、可扩展、安全
  3. JWT的优势：无状态、易于扩展、性能好
  4. JWT的安全：依赖于强算法和密钥安全
  5. JWT的最佳实践：使用刷新Token、合理设置过期时间、验证所有声明

记住：JWT不是万能的，它只是认证和授权的一种方式。选择合适的认证方式取决于你的应用场景和需求。对于新项目，特别是API服务，我们强烈推荐使用JWT认证。
